# План правок: потеря конкретики ТЗ между analyst, оркестратором и агентами

Проверено на этой версии (`mas-pipeline-integrated`) на живом прогоне `4fbcfc70` (сервис заметок, BACKEND + WEB).

## Что подтвердилось

| Тезис | В этой версии | Доказательство |
|---|---|---|
| Оркестратор сжимает ТЗ при планировании | **Да** | `context` агентов содержит только стек и порт: BACKEND — `{database, framework, language, port}`, WEB — `{framework, port, api_base_url}`. User stories, сущности и описание из `specification.json` в `context` не попали; `task` — пересказ на ~500 символов |
| Нет требования переносить тексты дословно | **Да** | Промпт `plan()` в `services/orchestrator/main.py`: «Context is domain-specific but contains all necessary requirements» — без требования дословности и без структуры |
| Нет проверки покрытия ТЗ | **Да** | `plan()` проверяет только роли, наличие `paths` и `acceptance_criteria`. Что каждая user story, сущность и критерий дошли до агента, не проверяется. Повтора при ошибке плана нет: одна неудача валит весь прогон |
| Агент не видит исходное ТЗ | **Да** | `component()` передаёт агенту только `task`, `context` плана и критерии своей роли. `specification.json` агентам не передаётся вообще |
| Схема analyst бедная | **Да** | В `ProjectRequirements` нет полей для функций, состава компонентов (в т. ч. админки), текстов уведомлений и интерфейса, демо-сценария, источников данных. Это негде сохранить, даже если модель это поняла |
| Analyst отдаёт одно и то же ТЗ на любой запрос | **Нет** | 6 прогонов дали разные ТЗ под свои запросы (см. `/app/output/*/specification.json`) |
| Фраза «context — только то, что нужно этому агенту» | **Не в этом месте** | Она есть в `services/mobile/orchestrator.py`, но тот планировщик в конвейере не используется: `mobile_agent.py` импортирует оттуда только вспомогательные функции. Аналогичная проблема — в промпте `services/orchestrator/main.py` |
| Критерии приёмки теряются | **Пока нет** | На прогоне `4fbcfc70` все 7 критериев перенесены дословно и разнесены по ролям верно. Но это поведение модели, а не гарантия кода |

**Потеря на входе подтверждена живым прогоном `e7e10a97`** (он дошёл до `completed` и выдал `project.zip`).
Пользователь написал заголовок «Мои заметки», поля «Заголовок» и «Текст», кнопку «Добавить». Analyst выдал
критерий `heading 'My Notes'`, историю `clicks 'Add'`, подписи полей пропали, а стек выдуман
(`Blazor WebAssembly 3.1`, `ASP.NET Core 3.1`). Оркестратор перенёс это в план, WEB-агент сделал страницу
«My Notes» / «Название» / «Создать заметку», а tester одобрил её, потому что проверял по искажённому критерию.
На предыдущих прогонах тот же запрос давал русские тексты дословно — поведение случайное. Итог: продукт
рабочий, но не соответствует требованиям, и ни одна проверка этого не замечает.

Про мобильный прогон (5 раундов, 47 минут, 272 тыс. токенов): здесь это не воспроизвести. MOBILE-агент этой версии не собирает Gradle сам, сборка идёт только в tester на Linux с KVM. Ожидание лимита (429 по 60 с) здесь видно у всех агентов.

## Правки

### 1. Оркестратор: исходное ТЗ доходит до агента без потерь (без участия LLM)

`services/orchestrator/main.py`, `component()`:
- добавить в `payload['context']` раздел `original_request` — исходный текст пользователя (`input.json`) **дословно**.
  Это единственный источник, который не прошёл через пересказ: analyst может перевести и сократить (см. прогон `e7e10a97`);
- добавить раздел `specification` — полный `spec` от analyst (он небольшой, единицы КБ);
- оставить `acceptance_criteria` роли, как сейчас.

Tester получает `requirements` из того же `context`, значит, тесты тоже будут строиться по исходному тексту.
В промпт `make_tests` добавить: «Если тексты в критериях расходятся с `original_request`, верен `original_request`».

Это закрывает потерю независимо от качества плана: WEB и BACKEND передают `context` проектировщику как справочный блок (лимит 100 тыс. символов), MOBILE получает его в `context`.

### 2. Оркестратор: промпт плана — структура и дословность

В `plan()` переписать требования к `context` и `task`:
- `context` — объект с разделами `features`, `scenarios`, `ui_texts`, `data_and_integrations`, `acceptance_criteria`, `stack_and_constraints`;
- всё, что относится к роли, переносится **дословно** (формулировки, числа, тексты сообщений). «Урезать» значит убрать чужие домены, а не сокращать свой;
- `task` — список того, что агент сдаёт, и сценарий, который должен работать.

### 3. Оркестратор: проверка покрытия в коде и повтор

После разбора плана:
- каждый элемент `user_stories`, `entities` (по имени), `api_endpoints` (метод + путь) и `acceptance_criteria` из `spec` должен встретиться в `context`, `task` хотя бы одного агента или в `contract.acceptance_criteria` (сравнение после нормализации регистра и пробелов);
- критерии приёмки `spec` должны попасть в `contract.acceptance_criteria` дословно, без пересказа;
- при нарушении — повторный вызов планировщика с перечнем потерянного (до 2 повторов), как и при других ошибках `plan()`. Сейчас повтора нет совсем.

### 4. Analyst: схема и промпт (решение за владельцем контейнера)

`services/analyst/app/schemas.py` и `prompts/analyst_system.txt`, только необязательные поля, чтобы не сломать текущий контракт:
- `components`: список `BACKEND | WEB | MOBILE` с назначением каждого (админка — явно);
- `features`: полный список функциональных требований;
- `ui_texts`: тексты уведомлений и интерфейса **дословно** из входа;
- `scenarios`: сценарии, включая демо-сценарий по шагам;
- `data_sources`: источники данных, mock-данные, адаптеры.

И в промпт: тексты интерфейса и уведомлений, названия и числа — дословно и на языке оригинала, без перевода;
стек не выдумывать — если пользователь его не задал, `null` (стек конвейера фиксирован: ASP.NET Core 10, Angular 20, Kotlin 2.2).

Порядок: сначала пункт 1 (дёшево, детерминированно и закрывает случай `e7e10a97`), затем 3, 2 и 4.

Пункты 1–3 перестают терять то, что есть. Пункт 4 добавляет то, чего сейчас нет. Без него админка и тексты уведомлений из кейса Russtech не дойдут.

## Проверка

1. Юнит-тест на проверку покрытия: план без одной user story отклоняется, и повторный запрос содержит её в перечне потерянного.
2. Живой прогон на тексте кейса Russtech: в `plan.json` каждый агент получает свои функции и тексты дословно, WEB (админка) выбран, а в `specification` агента есть всё ТЗ.
3. Сравнить с прогоном `4fbcfc70`: число раундов исправления и расхождений на стыках (имена полей, тексты).

Для шага 2 нужен файл кейса. «Кейс Russtech.pdf» в `C:\Users\RC\Downloads` не найден.
